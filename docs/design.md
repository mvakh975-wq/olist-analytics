# Olist Analytics — проектный документ

Дата: 2026-10-13 · Статус: согласован; §5 обновлён 2026-10-13

## 1. Цель

Портфолио-проект для резюме **аналитика данных (общий профиль)**. Показывает полный цикл:
бизнес-вопрос → SQL-модель данных с проверками качества → анализ и статистика → выводы с
рекомендациями → публичный дашборд.

**Критерий успеха:** рекрутер за 2 минуты по README и ссылке на дашборд видит бизнес-вопросы,
3–5 выводов, подкреплённых цифрами и рекомендациями, работающий дашборд, аккуратный SQL и
проверки данных. Проект воспроизводится локально тремя командами.

**Язык:** README, дашборд и выводы на английском; `README.ru.md` — русская версия README.

## 2. Данные

- Источник: [Brazilian E-Commerce Public Dataset by Olist](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce), Kaggle, 9 CSV.
- Лицензия: CC BY-NC-SA 4.0 — указываем авторство, некоммерческое использование, производные
  данные (витрины) публикуются под той же лицензией.
- Загрузка: `scripts/download.py` через Kaggle API (токен в `~/.kaggle/kaggle.json` или
  переменные окружения `KAGGLE_USERNAME` / `KAGGLE_KEY`). Если токена нет — понятная ошибка с
  инструкцией, как скачать архив вручную и куда положить.
- Используем все таблицы, кроме `geolocation` (география — на уровне штатов из customers/sellers).
- Все цифры в выводах — только из расчётов по этим данным; ничего не утверждается заранее.

## 3. Бизнес-вопросы

Отчёт от лица аналитика маркетплейса для руководства.

| # | Вопрос | Метрики / метод |
|---|--------|-----------------|
| 1 | Как растёт бизнес? | GMV, заказы, средний чек, доля доставки в чеке по месяцам; вклад категорий в рост |
| 2 | Возвращаются ли клиенты? | Месячные когорты по первой покупке, retention по месяцам, доля повторных покупателей. Клиент = `customer_unique_id` (не `customer_id`, который уникален на заказ) — эффект ошибки показываем отдельно |
| 3 | Кто наши клиенты? | RFM-сегментация; если повторных покупок мало и Frequency почти константа — метод адаптируется (например, R+M), решение описывается |
| 4 | Влияет ли доставка на удовлетворённость? | Оценка отзыва vs опоздание и его величина; статистический тест, размер эффекта, доверительный интервал; оговорка «корреляция ≠ причинность», проверка в разрезе региона и категории |
| 5 | Где проблемы логистики? | Доля опозданий и средняя задержка по штатам и продавцам; разница обещанного и фактического срока |

Итог — блок **Key findings → Recommendations** (3–5 пунктов) на главной странице дашборда и в README.

**Вне рамок:** ML-прогноз оттока, NLP по текстам отзывов, геокарты по координатам.

## 4. Архитектура

```
Kaggle (9 CSV) ─► scripts/download.py ─► data/raw/            (не в git)
   ─► dbt-duckdb: staging ─► intermediate ─► marts  → olist.duckdb (не в git)
   ─► scripts/export_marts.py ─► data/marts/*.parquet         (в git)
   ─► notebooks/ (анализ, статистика)
   ─► scripts/export_marts.py site-data ─► site/src/data/*.parquet (агрегаты для страниц)
   ─► site/ (Observable Framework: SQL-блоки на DuckDB в браузере + Observable Plot) ─► GitHub Pages
```

Витрины в git позволяют CI собрать сайт без доступа к Kaggle.

### 4.1 Слои dbt

- **staging** (`stg_<таблица>`): одна модель на источник; приведение типов (timestamp), имена
  колонок, перевод категорий на английский через таблицу-справочник, дедупликация отзывов
  (если профилирование найдёт дубликаты — правило выбора фиксируется в `docs/data_quality.md`).
- **intermediate**: `int_orders_enriched` — одна строка на заказ: сумма товаров, доставка,
  сумма оплат, даты покупки/доставки/обещанной доставки, задержка в днях, флаг опоздания,
  оценка отзыва, `customer_unique_id`, штат клиента.
- **marts**:
  - `fct_orders`, `fct_order_items`
  - `dim_customers`, `dim_sellers`, `dim_products`
  - `mart_monthly_kpis` — вопрос 1
  - `mart_cohort_retention` — вопрос 2
  - `mart_rfm` — вопрос 3
  - `mart_delivery_performance` — вопросы 4–5

Определения метрик (что входит в GMV, какие статусы заказа считаются, как считается задержка)
фиксируются в `dbt/models/marts/_marts.yml` и на странице Methodology.

### 4.2 Качество данных

1. `notebooks/00_data_profiling.ipynb`: пропуски, дубликаты, типы колонок, диапазоны дат по
   каждой таблице → `docs/data_quality.md` (проблема → решение).
2. dbt-тесты: `unique` / `not_null` на ключах, `relationships`, `accepted_values` для статусов;
   кастомные: дата доставки ≥ даты покупки (для доставленных), сумма оплат ≈ товары + доставка
   (с допуском, расхождения задокументированы).

### 4.3 Анализ

`notebooks/01_growth`, `02_retention`, `03_rfm`, `04_delivery_vs_reviews` — читают витрины из
DuckDB. Статистика: scipy (тесты, бутстрап-интервалы). Выводы ноутбуков переносятся в текст
дашборда; числа в тексте дашборда подставляются запросами к витринам, а не вписываются руками.

## 5. Дашборд (Observable Framework)

Изначально планировался Evidence.dev; к октябрю 2026 его разработка перешла в облачный
Evidence Studio, а открытая версия перестала развиваться. Выбран Observable Framework:
статическая сборка, SQL-блоки (DuckDB-WASM) прямо на страницах, графики Observable Plot.
Страницы читают небольшие агрегаты, подготовленные из витрин, а не сами витрины.

Страницы: **Overview** (выводы + KPI со сравнением к прошлому периоду), **Growth** (фильтры:
период, штат, категория), **Retention** (тепловая карта когорт, кривые удержания),
**Customers** (RFM-сегменты и действия), **Delivery & Satisfaction**, **Methodology** (источник,
лицензия, качество данных, ограничения).

Оформление: сдержанная палитра, один акцентный цвет + один сигнальный (для негативных значений),
подписи осей и единицы (BRL, дни, %), без градиентов и эмодзи; заголовок графика — вывод, а не
тема. Работает на ширине телефона.

## 7. Инструменты

- Python 3.12 через uv (3.14 не используем, пока его не поддерживает dbt — проверить).
- dbt-core + dbt-duckdb, DuckDB, pandas, scipy, Jupyter.
- Observable Framework (Node.js) для сайта.
- Стиль: ruff (Python), sqlfluff (SQL, диалект duckdb + шаблонизатор dbt).
- Версии зависимостей фиксируются (uv.lock, package-lock.json).

## 8. Проверки

- **CI (каждый push):** `dbt build` на фикстурной выборке, pytest, ruff, sqlfluff.
  - Сырые данные в CI недоступны, поэтому `dbt build` в CI идёт на небольшом фикстурном наборе
    CSV в `tests/fixtures/` (несколько десятков строк, вырезанных из реальных данных, с
    указанием лицензии). Полный `dbt build` — локально перед экспортом витрин.
- **pytest:** download.py (без сети, ошибки и распаковка), export_marts.py, сверочные тесты:
  GMV и число заказов в витринах совпадают с прямым расчётом по staging.
- **Сайт:** сборка Observable Framework в CI; локально — Playwright: все страницы на десктопе и телефоне,
  светлая и тёмная тема (если Evidence поддерживает), нет ошибок в консоли; скриншоты в README.
- **Деплой:** `pages.yml` собирает сайт из закоммиченных витрин и публикует на GitHub Pages.

## 10. Риски

| Риск | Что делаем |
|------|-----------|
| Повторных покупок очень мало → когорты и RFM малоинформативны | Это сам по себе вывод; адаптируем RFM, фокус на первой покупке и опыте доставки |
| Инструмент дашборда меняет модель (так случилось с Evidence) | Перешли на Observable Framework; сайт собирается из закоммиченных агрегатов, зависимость зафиксирована в package-lock |
| dbt не поддерживает выбранную версию Python | Фиксируем 3.12 через uv |
| Нет токена Kaggle | Ручная загрузка архива, инструкция в README |
